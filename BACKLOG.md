# Backlog

Не срочные, но подтверждённые баги/улучшения. Не реализовывать без явного запроса.

## 1. Ставка по тегу не запоминается при ручном добавлении/редактировании записи

Механизм «запомнить последнюю ставку по тегу» (`tagLastRate`, [dist/index.html](dist/index.html)) уже существует, но реализован только в живом таймере:
- запись: `saveEntry()` (~строка 1692) — `tagLastRate[currentProjectTag] = rateVal`
- чтение: `selectProject(t)` → `updateRateForTag(t)` (~строки 1646, 2613) — подставляет `tagLastRate[tag]` в поле ставки при выборе тега

В Истории этого нет вообще:
- `saveNewEntry()` (~2438, форма «+ Добавить») — не читает и не пишет `tagLastRate`
- `saveDdEdit()` (~2457, инлайн-редактирование записи) — то же самое
- выбор тега в `editFieldsHtml()` (~2218) не вызывает ничего похожего на `updateRateForTag`

Поэтому для клиента с фиксированной часовой ставкой, если запись создаётся/правится через Историю (а не через Таймер), ставку приходится вводить заново каждый раз — именно это увидел пользователь.

**Что делать:** при выборе тега в формах Истории — подставлять `tagLastRate[tag]`, как это уже делает Таймер; при сохранении — обновлять `tagLastRate[tag]`, как это делает `saveEntry()`.

## 2. Числа дней в календаре визуально «скачут» по высоте

`.cal-day` — flex-колонка с `justify-content: center` (dist/index.html, ~строка 522), где по вертикали центрируется весь блок целиком (`.num` + опционально `.hrs`). У дня с часами блок из двух строк, у дня без записей — из одной, из-за этого сама цифра дня (`.num`) стоит на разной высоте в зависимости от того, есть ли под ней бейдж часов — календарь выглядит «прыгающим» по горизонтали одного ряда.

**Что делать:** не центрировать весь стек, а закрепить `.num` в одной и той же позиции независимо от наличия `.hrs` — например, `justify-content: flex-start` с фиксированным отступом сверху, либо всегда резервировать место под `.hrs` (пустым, если часов нет), чтобы `.num` никогда не сдвигался.

## 3. Статистика «Задач» в Истории считает записи, а не уникальные задачи

`computeStatsForRange()` (dist/index.html, ~строка 2645) делает `count++` на каждую запись в `dayDetails[key].entries`, без группировки по названию. Если несколько дней подряд работать над одной и той же задачей (несколько отдельных записей с одинаковым `title`), плитка «Задач» в Истории покажет 2, 3 и т.д. вместо 1.

Показательно, что в другом месте приложение уже считает «одинаковое название = одна задача»: `buildInvoicePdf()` (~строка 3610) группирует записи по `title + currency` (`rowsByKey`) при формировании строк счёта — то есть нужная логика группировки уже есть, просто не переиспользована для этого счётчика.

**Что делать:** в `computeStatsForRange()` считать `count` как число уникальных `title` (или `title + tag`, если задачи с одинаковым названием в разных проектах должны считаться разными) в отфильтрованных записях, а не общее число записей — часы и деньги при этом продолжают суммироваться по всем записям как сейчас.

## 4. Нет быстрого выбора повторяющегося названия задачи

Поле названия задачи — обычный текстовый инпут без каких-либо подсказок:
- Таймер: `#titleInput` (dist/index.html, ~строка 685) — просто `<input type="text">`, плейсхолдер и всё
- История: те же текстовые поля в `saveNewEntry()`/`saveDdEdit()`

Если задача повторяется день за днём («Landing page design» и т.п.), название приходится каждый раз перепечатывать вручную — нет способа выбрать его из уже использованных.

Похожий паттерн уже реализован для тегов: `.combo-wrap`/`.tag-popover` с поиском и списком (`toggleProjectPopover`, `renderProjectOptions`) — по такому же принципу можно сделать подсказку/поповер и для названия задачи.

**Что делать:** под полем названия (в Таймере и в формах Истории) показывать список ранее использованных названий — по клику в поле или при вводе, с фильтрацией по введённому тексту, выбор одним кликом подставляет название. Источник данных — уникальные `title` из `dayDetails` по всем датам; имеет смысл в первую очередь показывать (или сортировать выше) названия, которые уже встречались под тем же тегом/проектом, раз речь о повторяющихся задачах у одного клиента.
